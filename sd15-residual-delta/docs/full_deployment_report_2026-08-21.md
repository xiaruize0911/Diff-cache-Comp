# 全量部署实验报告:所有 240 个缓存位置的训练与部署

日期:2026-08-21 · 模型:SD1.5,512×512,30-step DDIM,CFG 7.5 · 硬件:单 A40

## 0. 结论

全量部署已完成并测量。**结果为负,且负结果是结构性的**:

- 在全部 240 个 reuse 位置部署 learned correction,**质量在所有注入幅度下都比无修正的 fixed cache 更差**(scale 1.0 时 MSE −5.00%、Gaussian SSIM −0.0053),速度从 1.311× 掉到 0.887×(比 exact 还慢)。
- 速度侧可以工程修复(CUDA graph 458.8→78.0ms,再加 inductor fusion →57.6ms,即 **1.240×**),但**结构上永远低于** fixed cache 的 1.311×:修正是缓存路径上的净增计算,最好情况只是"代价可忽略"。即便做到 compute 理论地板也仅 1.287×。
- **oracle 上界实验证明这不是预测器容量/数据/训练方式的问题**:即使把预测残差换成真实残差(完美 corrector),在 60 个位置上也只能拿回可用质量差距的 13%。
- "更激进 schedule + 修正" 这条路径同时在两个轴上劣于基线。

因此 "显著的质量和速度同时提升" 在 SD1.5 的 attention-residual 复用框架内不可达。

## 5. 速度侧:launch 开销、fusion 与结构性渐近线

surrogate 单次调用耗时与张量规模几乎无关(320ch@64² 约 5.02 GFLOP 与 1280ch@8² 约 0.1 GFLOP 耗时相同),说明 eager 模式下是 **kernel launch 开销主导**。

Roofline(320ch@64²,width 128,depth 3,batch 2):

| 界 | 数值 |
|---|---:|
| compute 5.02 GFLOP @ 60 TFLOPS | 0.084 ms |
| HBM 未 fuse(~23 kernels,中间张量反复往返 112 MB) | 0.161 ms |
| HBM 理想 fuse(24 MB) | 0.035 ms |

三种实现实测:

| 实现 | 320ch@64² | 640ch@32² | 1280ch@16² | 1280ch@8² | 240 次/张图 | 投影速度 |
|---|---:|---:|---:|---:|---:|---:|
| eager | 1.922 ms | 1.880 ms | 1.896 ms | 2.099 ms | **458.8 ms** | 0.899× |
| CUDA graph(仅消 launch) | 0.527 | 0.257 | 0.218 | 0.187 | **78.0 ms** | 1.216× |
| `torch.compile` fusion + graph | **0.386** | **0.197** | **0.155** | **0.149** | **57.6 ms** | **1.240×** |
| compute-bound 理论地板 | ~0.084 | — | — | — | ~19 ms | 1.287× |
| fixed cache 基线(无修正) | — | — | — | — | 0 | **1.311×** |

**修正:先前把全量部署的速度记为 0.887× 是 unfused eager 的伪影。** CUDA graph 消除 launch 开销得到 1.216×,inductor fusion 在此之上再拿 1.35×(78→57.6 ms)得到 1.240× —— 真实速度代价只比基线低约 5%,如果质量为正是完全可接受的。

但有一条 fusion 改变不了的结构性事实:

```text
speedup = T_exact / (T_fixed + C),  C >= 0
```

修正是在缓存路径之上**净增**计算,最好情况是"代价可忽略",不可能是"负代价"。**全量部署的速度渐近线是从下方逼近 fixed cache,永不超过**:即便做到 compute 地板(19 ms)也只有 1.287× < 1.311×。

残余工程空间:compiled 的 0.386 ms 距理想 fuse 内存地板(0.035 ms)与 compute 地板(0.084 ms)仍有 3–4×,说明 inductor 未能把 1×1 conv 融进 GEMM 链;手写 fused kernel 估计可达 240 次约 25–30 ms。但这是为一个质量上限已被证明很低的方向做投入。

## 6. Oracle 上界:决定性实验

把选定位置的缓存残差替换为**真实计算的残差**(`oracle_refresh_keys`),这是任何 corrector 在这些位置的理论最优。

| 变体 | 修正位置 | 速度 | Δssim | ΔLPIPS% | 占可用差距 |
|---|---:|---:|---:|---:|---:|
| fixed cache | 0 / 240 | 1.253× | — | — | 0% |
| oracle m14 | 15 | 1.224× | +0.0095 | +7.90 | 8.0% |
| oracle m14+13 | 30 | 1.213× | +0.0139 | +12.05 | 11.7% |
| oracle top4 | 60 | 1.159× | +0.0156 | +12.97 | **13.1%** |
| oracle 全 16(= exact) | 240 | 0.997× | +0.1193 | +100 | 100% |

**完美修正 25% 的缓存工作量,只能拿回 13% 的质量差距**,收益次线性而成本线性。这排除了"预测器容量不够""训练数据不够""分布偏移"等所有解释——缓存造成的质量损失均匀分布在 240 个位置上,修好少数几个帮助有限。

另一个值得注意的现象:oracle 修正让 SSIM/LPIPS 改善,但 **MSE 反而略微变差**(−0.35% 到 −0.94%)。部分修正会把轨迹推到一个像素级 MSE 更差、但感知指标更好的位置。

## 7. 最后一条路径:激进 schedule + 修正

假设("大 K 配强 C"):把 anchor 减到 `[0-8, 12, 20, 28]`(12 exact / 18 reuse,max K=7)换取速度,再用修正补回质量。

| 配置 | 速度 | Δ速度 | Gaussian SSIM | Δssim |
|---|---:|---:|---:|---:|
| extra10 / fixed(基线) | 1.253× | — | 0.8807 | — |
| aggressive / fixed | 1.354× | **+0.101** | 0.7591 | **−0.1216** |
| aggressive / oracle top4 | 1.225× | −0.028 | 0.8006 | −0.0800 |

激进 schedule 确实更快(+0.101),但质量崩塌 −0.1216;即使配上**完美** corrector,也只恢复到 −0.0800,同时速度掉到 1.225×(低于基线 1.253×)。**两个轴同时劣于基线**,该路径被否证。

## 9. 结论与建议

1. **全量部署已完成并测量,结果为负。** 训练覆盖全部 240 个位置的共享 surrogate 是可行的(数据量提升 32×,残差改善 15.4%),但部署后质量在所有幅度下都劣于不修正。
2. **负结果是结构性的,不是实现问题。** oracle 上界证明即使完美预测也只能拿回 13% 的差距。继续增加模型容量、训练数据、或改用迭代式 on-policy 训练(修正上游分布偏移)都不会改变这个上限。
3. **此前的单点正向结果不泛化**,同 module 同 scale 铺开后符号翻转,应视为位置特异的感知偏置伪影。
4. **速度天花板独立成立**:attention 仅占端到端 41%,全部缓存的理论上限 1.70×;而修正是净增计算,与提速方向相反 —— fusion 可把代价压到约 5%(1.240× vs 1.311×),但渐近线永远在基线之下。
5. **建议**:若要继续这个方向,应换到 attention 占 80–95% FLOPs 的 DiT 类骨干(FLUX/SD3),那里天花板是 5–10×,且 oracle 上界需要重新测量——本报告的结论只对 SD1.5 的 U-Net 成立。在 SD1.5 上,**correction-free 的 anchor schedule 选择仍是唯一有效的手段**。
