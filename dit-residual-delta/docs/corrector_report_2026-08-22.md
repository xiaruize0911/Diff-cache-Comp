# 在 PixArt-Σ 上重训修正器 C:结果与机制

日期:2026-08-22 · PixArt-Σ-XL-2-512-MS,512×512,20-step,CFG 4.5,fp16 · 单 A40
prompt 划分按**主体**不相交(train 112 / val 24 / test 24),指标全部相对同 seed 的 exact 输出。

## 0. 结论

1. **残差侧,DiT 与 SD1.5 完全不是一个量级。** 一个闭式的分组岭回归就能把
   per-block 的 `ΔR` 相对 MSE 压到 **0.058**;训练出的共享 C(21M)达到 **0.0537**。
   SD1.5 arm 上训练出来的 surrogate 是 **0.846**,差 16 倍。
2. **但残差精度越高,部署后图像越差 —— 单调反向。** 这不是噪声,是结构性的:
   把修正注入点从 28 个/步减到 1 个/步,残差精度从 0.054 退化到 0.317,
   而图像质量从"彻底崩坏"变成"**唯一一个超过 correction-free 前沿的配置**"。
3. **机制是深度方向的误差放大。** fixed cache 的每块误差与状态无关,偏差沿深度
   **相加**;一个*有效的*修正器让每块输出跟踪真实块,偏差递推变成
   `δ_{b+1} = (I + J_b) δ_b + ε_b` —— 沿 28 层**相乘**。修正器越准,越像真实块,
   放大越强。
4. **正向结果**:整栈作为单个缓存单元 + 一个 C,在留出集上比 correction-free 前沿
   高 **+0.02 ~ +0.03 SSIM / −0.03 ~ −0.05 LPIPS**(等速比较,3.0–3.3× 区间),
   逐 case 配对 t = 3.9~6.4。C 的速度代价 25 ms(约 9%)。
   附带一个与修正器无关的白拿加速:整栈粒度的 fixed cache 比逐块粒度快 **10.5%**,
   两者输出逐比特相同。

## 1. 数据与训练管线

on-policy 采集:在 i5(anchor `{0,5,10,15}`)的 cached rollout 上,每个 reuse slot
额外跑一次真实块拿到真值残差,但**传播仍用缓存值**,所以记录到的状态就是部署时
C 会遇到的状态 —— SD1.5 arm 踩过的 teacher-forcing 暴露偏差在这里从构造上避免了。

C 的结构与 SD1.5 版对齐(共享模型 + AdaLN 条件 + 零初始化输出,未训练时严格等于
fixed reuse),差别是 token-wise 而非卷积,并且加了一条**按块的低秩线性通路**
(`ΔR += (x A_b) B_b`)—— 岭回归诊断显示 `ΔR` 主要是输入的线性函数(Jacobian 一阶项),
让共享 MLP 去重新推导这件事很浪费容量。

| 配置 | 参数 | val rel_mse |
|---|---:|---:|
| 共享 MLP w256 d3 | 2.63M | 0.1174 |
| + 低秩线性通路 r64 | 10.89M | 0.0643 |
| + r128 / w384 | 21.31M | **0.0537** |
| w512 d4(无线性通路) | 9.26M | 0.0598 |
| 参照:按 (block,horizon) 分组的闭式岭回归(446M) | — | 0.0580 |
| 参照:SD1.5 arm 训练出的 surrogate | 2.34M | 0.8460 |

低秩线性通路用 1/40 的参数就追平了 446M 的分组闭式解。

## 2. 部署失败与定位

把 rel_mse 0.0537 的 C 接进 rollout,图像**崩溃**:i2 的 SSIM 0.678 → 0.123,
速度也从 1.76× 掉到 1.20×(448 次/图的 eager 调用)。

排查顺序与结论:

1. **先怀疑接线,并且确实先找到一个自己的 bug**:timestep 的 Fourier 嵌入在部署时
   跑在 fp16 下。相位量级到 1000,而 fp16 在 1000 附近的间隔是 0.5,`cos/sin` 的结果
   与训练时的 fp32 值毫无关系。修好后补了一个等价性测试
   (`scripts/verify_bank.py`):部署用的 fp16 通路必须在真实采集数据上复现 fp32
   训练通路,实测相对漂移 **5.3e-6**,rel_mse 复现为 0.0588。
2. **修好之后仍然崩溃**,于是做开环 on-policy 诊断
   (`scripts/diagnose_closed_loop.py`):让 C 预测但**不注入**,在 C 本该工作的
   轨迹上量它的误差 —— **rel_mse 0.0658**,与训练值一致。所以 C 是准的,
   runtime 喂给它的输入也是对的。
3. 因此崩溃是**闭环反馈**,不是精度不够,也不是 bug。

误差递推:设 δ_b 是复用分支相对精确轨迹在第 b 块的偏差。

```text
fixed cache: out_b = h_b + R_a,b        -> δ_{b+1} = δ_b + (R_a,b - R_b(h*_b))   相加
learned  C : out_b ≈ h_b + R_b(h_b)     -> δ_{b+1} ≈ (I + J_b) δ_b + ε_b          相乘
```

`R_a,b` 与当前状态无关,所以 fixed cache 没有反馈增益;一个**工作正常的** C 恰恰
恢复了对当前状态的依赖,于是把误差递推变成沿深度相乘。28 层一乘就爆。
开环诊断里 horizon-1 的 `pred_rms/target_rms ≈ 1.5`,系统性高估 1.5 倍,
沿 28 块复合即为灾难。

## 3. 用注入粒度 K 把这个权衡量出来

把 28 块划成 K 个连续段,每段作为**一个**缓存单元,每步每段只注入一次。
K=28 是逐块(原设计),K=1 是整栈。

先记一个有用的恒等式(有单测):**任意连续划分的 fixed cache 输出完全相同**,
都等于 `h_t + Σ_b R_a,b`。所以 K 只改变修正器的注入结构,不改变 correction-free
基线 —— 这让比较是干净的。(附带好处:K=1 少了 28 次 Python 层块调用,
i5 下 fixed cache 从 3.33× 提到 3.69–4.54×,白拿。)

| K | 每段块数 | val rel_mse | i5 部署最好 SSIM | 相对 fixed_i5 (0.3868) |
|---:|---:|---:|---:|---:|
| 28 | 1 | **0.0537** | 0.0752 | **−0.3115** |
| 4 | 7 | 0.2021 | 0.3564 | −0.0304 |
| 2 | 14 | 0.2724 | 0.3831 | −0.0036 |
| 1 | 28 | 0.3166 | **0.4581** | **+0.0713** |

**残差精度与部署质量严格反向。** 这条曲线本身就是机制的证据:唯一变化的是
注入点数量,而它主导了一切。

## 4. 正向结果:K=1 超过 correction-free 前沿(留出集确认)

**速度单独重测。** 本轮早期的 speedup 数字不可信:当时 GPU 上还有另一个评测进程,
同一次运行内 exact 的耗时从 0.99 s 漂到 2.18 s。重新写了
`scripts/benchmark_speed.py`:独占 GPU(检测到别的进程就拒绝启动)、
exact 与变体 A/B 交替、每个配置 10 次重复、checkpoint 预加载(否则 `/workspace`
的 25 MB/s 读取会被算进计时,表现为 4–7 s 的"变体耗时")。下表速度全部来自该基准。

## 5. 与 blend 上界的关系(修正上一份报告的一个推断)

`docs/dit_gate_report_2026-08-21.md` 用 α 混合(`ΔR̂ = α·ΔR`)测出"要恢复一半质量
差距需要 α≈0.90,即 rel_mse ≤ 0.01",并注明该映射假设误差与真值共线。
本轮结果说明**这个注记比当时想的要紧得多**:

- α 混合的误差是缓存误差的**收缩**,方向安全,不引入状态依赖,所以不放大。
- 真实 C 的误差方向任意,并且恰恰因为 C 有效而引入了状态依赖,沿深度放大。

量化对比最能说明问题:blend 在 `rel_mse = 0.0625`(α=0.75)时回收 **+26%** 的质量差距;
而学习出来的 C 在 `rel_mse = 0.0537`(**更准**)逐块部署时是 **−74%**。
**同样的 rel_mse,共线误差与任意方向误差之间差了一整个符号。**

因此 blend 曲线不是学习式修正器的可用上界,只能当作"误差方向最有利时"的参考。
上一份报告写的 "rel_mse ≤ 0.01" 门槛应当作废:可用的判据必须是**在部署粒度下测的
闭环量**(部署后与 correction-free 前沿的等速比较),而不是残差空间的开环量。

## 7. FLOPs 口径的精度/加速汇总

用 `torch.utils.flop_counter.FlopCounterMode` 在真实 pipeline 调用上直接数
(`scripts/count_flops.py`),VAE decode、patch embedding、所有投影都算在内。
**注意不能在 `torch.inference_mode()` 下数 —— inference tensor 绕过 Python dispatch,
计数器会静默返回 0。** 交叉验证:exact 54.06 TFLOP 与 28 block 的解析估算(约 53 TFLOP)
一致;`fixed_i5` 与 `fixed_i5_K28` 计数**完全相同**(12.944),印证了分段恒等式
—— 两者 10.5% 的 wall-clock 差距纯粹是 Python 层派发开销。

## 8. 下一步

1. **DAgger**:`collect_features.py` 已支持 `--surrogate-checkpoint`,可以在 C 自己产生的
   轨迹上重新采集再训。K=1 的 `rel_mse` 0.317 里有多少来自分布偏移,这一步能直接回答,
   也是目前最可能把 +0.03 SSIM 推上去的一招。
2. **把损失换成闭环损失**:现在训练惩罚的是当步残差,部署在意的是**传播之后**的误差。
   这正是 loss 与目标脱节的地方;对 K≥2 尤其关键。
3. **不要再加宽 C**:31.56M 比 11.88M 更差(0.354 vs 0.317),限制是数据(5376 slot)
   与任务本身的非线性,不是容量。
4. **K=1 的免费加速可以立刻用**:与修正器无关,输出逐比特相同,i5 下 +10.5%。
